# BlackFriday Watchtower

**A concurrent multi-agent watchtower for a synthetic Black Friday store** — built on
[Mozaik](https://docs.jigjoy.ai) (`@mozaik-ai/core` **v4.2.0**, pinned — see "Version note").

> **SYNTHETIC DATA ONLY.** Every order, customer, and dollar in this repo is generated by a
> seeded generator in this repo. No real customers, no real money, no real accounts.
> This is an operations demo — **not financial advice**.

A small store's Black Friday rush, run by a room of agents that work **at the same time, on
the same bus, over the same shared ledger** — and that are not allowed to move money on
their own say-so. Any state-changing action (issuing a refund, voiding an order) must pass
an **interception gate** that demands **two independent confirmed evidence sources** first.

---

## Run it (3 steps, no API key needed)

```bash
git clone <this repo> && cd watchtower
npm install
npm start
```

Then open **http://localhost:8788** — the web console shows the room working live:
agent roster, the event feed, the guard strip (BLOCKED / ESCALATED / ALLOWED), the ledger,
and the audit trail. When the $1,232 refund escalates, **click Approve** on its card and
watch the room retry and complete it.

Other modes:

```bash
npm run demo       # same scenario in the terminal (operator auto-approves, and says so on the record)
npm run selftest   # headless run + 10 assertions on the full story arc (exit code = verdict)
npm run smoke      # 60-second proof of the gate mechanics: BLOCK without evidence, ALLOW with it
```

**LLM mode (optional):** `WATCHTOWER_MODE=llm MOZAIK_MODEL=gemini-3.5-flash GEMINI_API_KEY=... npm start`
uses Mozaik's default inference runner and a real model drives the same agents through the
same tools and the same gate. Deterministic mode is the default so judges can run the repo
with zero keys; in deterministic mode a policy `InferenceRunner` (an official Mozaik
extension point, `src/runner.ts`) plays the model's role with explicit, inspectable rules —
the gate, the tools, the bus, and the shared state are identical in both modes.

## What happens in the demo (one story arc)

1. **OrderFeed** streams 26 synthetic orders. **Watchtower** scores every order against the
   fraud rules; **LedgerKeeper** books every order into the shared ledger — concurrently,
   reacting to the same events.
2. A weak flag (billing/shipping city mismatch only) → the **Auditor** recomputes it from
   source and **HOLDs** it: one weak signal is not evidence.
3. A strong flag (velocity + chargeback history) → LedgerKeeper tries to void at once → the
   **EvidenceGate BLOCKS it** (only the ledger's evidence exists) → Auditor verifies →
   retry → **ALLOWED** → order voided, ledger reversed.
4. Refund request **REQ-501** ($238, flagged order) → the clerk races the Auditor → executes
   once two evidence sources exist.
5. Refund request **REQ-502** ($1,232) → evidence is sufficient but the amount is above the
   $500 threshold → **ESCALATED** → a human approves in the console → **ALLOWED** → refunded.
6. **Scribe** (pure observer) writes the whole thing into an audit trail where **every number
   cites its source**: order id, ledger line id, request id, or evidence id.

## How our agents run concurrently

There is no orchestrator and no pipeline. All participants share **one Mozaik event bus**
and **one `RuntimeState`** (order book, ledger, evidence register). Each agent is a set of
*situation handlers* — "when X happens on the bus, I act" — so a single `order.received`
event wakes Watchtower and LedgerKeeper **simultaneously**, and a single `order.flagged`
event wakes the Auditor and LedgerKeeper at the same moment. Agents never call each other;
they publish typed events and contract-token messages (`FLAG:`, `HOLD:`, `REFUND:`,
`EVIDENCE:`) and react to what they observe.

Concurrency is real, not staged: the RefundClerk and the Auditor genuinely race on a fresh
flag, and the gate's verdict depends on which evidence has landed in shared state by the
time the gated tool call is attempted. Agent loops get a **fresh `ModelContext` per task**
(shared state lives in `RuntimeState`, not in chat memory), so parallel loops of the same
agent cannot contaminate each other's context.

The **Auditor is independent by construction**: it reads the bus and the source data
(order + ledger), never the flagger's private reasoning, and its confirmations are one of
only three evidence sources the gate accepts (ledger, auditor, human operator). A flag is
not evidence; a proposal is not evidence; no agent can authorize its own action.

## Architecture

```
                ┌──────────────────── one Mozaik runtime ────────────────────┐
                │  RuntimeState: orderBook · ledger · confirmedEvidence       │
                │                                                             │
  OrderFeed ──order.received──▶ Watchtower ──FLAG:──▶ Auditor ──EVIDENCE:/HOLD:
       │                            │                     │                   │
       └──────────────▶ LedgerKeeper ◀── ledger.updated ──┘                   │
                             │  ▲                                             │
                             │  └──── void_order ──▶ ╔═══════════════╗        │
  Operator ──refund.requested──▶ RefundClerk ── issue_refund ──▶ ║ EvidenceGate ║
       │                                                        ║ ≥2 evidence ║
       └──human.decision (console Approve/Reject)──▶            ║ or BLOCKED  ║
                                                                ╚═══════════════╝
  Scribe (observer) ──▶ audit trail        Console (SSE) ──▶ browser
```

| Participant | Role |
|---|---|
| **OrderFeed** | Feed: streams synthetic orders, owns intake into the shared order book |
| **Watchtower** | Scores each order against the fraud rules (`search_orders`, `get_order`, `flag_order`) |
| **LedgerKeeper** | Books every order (`record_ledger_entry`); voids high-severity orders (`void_order`, gated) |
| **RefundClerk** | Answers refund requests (`draft_reply`, `issue_refund`, gated) |
| **Auditor** | Independently recomputes flags from source (`get_order`, `get_ledger_line`, `confirm_evidence`, `raise_hold`) |
| **Scribe** | Pure observer: live timeline + audit trail |
| **Operator** | Human: injects refund requests, approves/rejects escalations |
| **EvidenceGate** | Not a participant — a Mozaik `InterceptionHandler` on the agent loops |

## Care with financial data

- **Every number has a source.** Flags cite rule ids and the exact order fields/order ids
  behind them; ledger lines cite the order or request that produced them; guard verdicts
  list the evidence sources counted. The final summary recomputes the balance from the
  ledger lines and prints MATCH/MISMATCH.
- **Synthetic, labelled, seeded.** The dataset (300 orders, 12 refund requests) is generated
  by `src/data.ts` with seed `20261127` and written to `data/` on every start — see
  [SYNTHETIC-DATA.md](SYNTHETIC-DATA.md). Fraud *labels* are rule outputs over synthetic
  data; no real-world precision is claimed.
- **Not financial advice** — banner in the console, note here, and the agents' instructions.

## Fraud rules (in `data/rules.json`, explained in SYNTHETIC-DATA.md)

| Rule | Signal | Strength |
|---|---|---|
| R1 VELOCITY | ≥4 orders from one device within 10 minutes (order ids cited) | medium |
| R2 ADDRESS_MISMATCH | billing city ≠ shipping city | weak — Auditor requires corroboration |
| R3 HIGH_VALUE_NEW_CUSTOMER | total > $900 and 0 prior orders | hard (history-backed) |
| R4 CHARGEBACK_HISTORY | ≥1 prior chargeback | hard (history-backed) |

Auditor's standard: a flag passes with **≥2 rule hits or ≥1 hard hit**; a lone weak/medium
signal is **HOLD** — "what is missing" is stated, not implied.

## Version note (why v4.2.0 is pinned)

`@mozaik-ai/core` latest moved to 5.x/6.x with a different API surface, while the official
docs describe v4. The v4 quickstart cannot run on 5.x/6.x (no `defineRuntime` /
`SituationSpecification` / `InterceptionHandler` exports), so this project pins **4.2.0** —
the version the docs, the mini-course, and the reference winner (OpsRoom) are built on.

## Layout

```
src/
  state.ts     RuntimeState: order book, ledger, evidence register, audit trail
  data.ts      seeded synthetic generator + fraud rule engine + auditor standard
  bus.ts       domain event types + situation specifications
  tools.ts     agent tools (flag / record / confirm / hold / refund / void)
  gate.ts      EvidenceGate — the InterceptionHandler
  runner.ts    deterministic InferenceRunner (LLM mode uses Mozaik's default)
  agents.ts    the seven participants and their situation handlers
  scenario.ts  the demo story arc
  server.ts    one-port SSE web console
  main.ts      entry points (web / --cli / --selftest)
  smoke.ts     gate mechanics proof
web/index.html the console
data/          generated dataset (orders.json, rules.json, refund_requests.json)
```
