# Synthetic data — how it is made and why you can trust the labels

Everything in `data/` is **generated by code in this repo** (`src/data.ts`) with a fixed
seed (`20261127`, mulberry32 PRNG). Same seed → same dataset, on every machine, on every
run. No real customers, no real transactions, no scraped data. The files are rewritten on
every `npm start` from the same generator, so the data can never drift from the code that
explains it.

## Files

| File | Contents |
|---|---|
| `data/orders.json` | 300 orders: id, timestamp, synthetic customer (name, `@example.test` email), items from a 20-product catalog, total (= exact sum of items), payment method, billing/shipping city, device id, `priorOrders`, `priorChargebacks` |
| `data/rules.json` | The 4 fraud rules, with plain-language explanations |
| `data/refund_requests.json` | 12 refund requests, each pointing at an order id; amounts equal the order totals |

## Planted patterns (the demo's story orders)

The first 26 orders — the ones the demo streams — contain four planted cases; the remaining
274 orders are mostly clean with the same patterns sprinkled at low density (so the full
dataset yields roughly 40 flags, like a real rush hour):

| Case | Construction | Expected room behavior |
|---|---|---|
| Weak flag | Address mismatch (R2) only | Auditor **HOLD** — a lone weak signal could be a gift purchase |
| Strong flag | 5-order burst from one device; the 4th also has `priorChargebacks=1` (R1+R4) | Void attempt **BLOCKED** → audit pass → void **ALLOWED** |
| Refund REQ-501 | Order with `priorChargebacks=1` (R4), total $238.00 | Refund executes once ledger + auditor evidence exist |
| Refund REQ-502 | New customer, total $1,232.00 (R3) | Refund **ESCALATED** (> $500) → human approves → executes |

## How a number earns its place

- An order's **total** is the sum of its item prices — checkable against `items` in
  `orders.json`.
- A **flag** cites the rule id and the exact fields behind it (for R1, the order ids
  counted in the window). The flag tool recomputes the rules from the order book; a flag
  cannot be asserted without the data producing it.
- A **ledger line** cites the order id (SALE), the request id (REFUND), or the SALE line
  it reverses (VOID). The closing balance is recomputed from the lines in the summary.
- **Evidence** is a register entry with a named independent source (`ledger:L-…`,
  `auditor`, `human-operator`). The gate counts distinct sources, never assertions.

## Honest limits

The fraud labels are **outputs of these 4 rules over synthetic data** — they demonstrate a
workflow, not a detection capability. No precision/recall is claimed, and nothing here
should be read as financial advice.
